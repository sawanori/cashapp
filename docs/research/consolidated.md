# 幹事向け会費集金アプリ — 調査統合レポート

統合日: 2026-09-24 / 統合者: 調査統合エージェント
入力: 引継ぎ書、ローカル環境メモ、7領域の一次資料レポート（paypay / stripe / line-miniapp / legal-jp / alt-providers / competitors / tech-stack）、および decision_critical 主張18件に対する3レンズ反証検証

**最初に結論を一文で。** 引継ぎ書の中心要件「参加者の支払いを検知して自動で支払済みチェックを付ける」は技術的には達成可能だが、当初希望の受取先「幹事の個人PayPay」を保ったまま達成する経路は、一次資料の範囲では存在しない。両立させる唯一の実在経路は「幹事が事業者性を持つ決済アカウント（加盟店）で受け取る」か「幹事の個人銀行口座＋電子決済等代行業経由の入出金明細照会」のいずれかであり、どちらも幹事側のオンボーディング負担が跳ね上がる。

## 0. このドキュメントの読み方

### 0-1. 三分離ラベル

各判断に次の3つを分けて付す。混ぜると必ず誤る。

- **[技術]** — 公開されているAPI・SDK・仕様で実装できるか
- **[規約]** — 決済事業者／配布プラットフォームの契約・規約・審査で許されるか
- **[法務]** — 日本法（主に資金決済法）上の整理が付くか

値は `可` / `条件付き可` / `不可` / `未確定`。

### 0-2. 確信度

- **高** — 一次資料の逐語引用があり、かつ3レンズ反証検証を通過した（または通過部分）
- **中** — 一次資料の逐語引用はあるが、反証検証で含意が訂正された、もしくは単一資料のみ
- **低** — 反証検証にかけられていない（decision_critical 除外分）、または取得失敗で未確認

### 0-3. 引用URLの扱い

本書に載るURLは、各領域レポートおよび反証検証エージェントが「実際にフェッチした」と記録しているものだけを転記している。**統合者自身は再フェッチしていない。** 実装着手前に再確認すべき重要URLは §5 に列挙した。

### 0-4. 検証カバレッジの正直な申告

decision_critical と判定された主張のうち **18件のみが3レンズ反証検証にかけられ、64件は未検証のまま除外された**。除外分は「一次資料レポートにそう書いてある」という以上の保証がない。特に以下は結論に強く効くのに未検証である: PayPay加盟店資格(PP-05)、PayPayオンライン手数料3.8%・月末入金(PP-07)、PayPayのNG商材(PP-11)、Stripe Connect×PayPayの4資料(F04–F07)、日本の入金デフォルト手動(F14)、資金移動業登録は株式会社限定(F6)、楽天銀行API(F13)、connpass/Doorkeeperの直接入金構造(F16/F17)、LINE×PayPay 2026年夏連携(PP-17/LMA-08/F20)。

## 1. 結論 — 引継ぎ書「10. 次に解くべき論点」1〜6への現時点の回答

### 論点1. 個人幹事向けの会費回収に使える正規サービスはあるか

**回答: 「一般個人（非事業者）のまま」という条件を厳守するなら、決済事業者ルートには存在しない。条件を1段緩めれば複数ある。**

- **[技術] 条件付き可（確信度 高）** — 加盟店決済の枠組みなら Webhook ＋ 照会API で参加者単位の検知が確実にできる。PayPay は `GET /v2/codes/payments/{merchantPaymentId}`、Stripe は `checkout.session.completed` ＋ Session 再取得、PAY.JP は `charge.succeeded`、PayPal は `PAYMENT.CAPTURE.COMPLETED`。
- **[規約] 不可〜条件付き可（確信度 高）** — API/Webhook を提供する主体は例外なく加盟店／ビジネスアカウントであり、加盟店登録には事業実態の証憑が要る。KOMOJU は「日本の法人様（法人および個人事業主を含む）のみ」と明記。Square は開業届またはそれに代わる書類を要求。PAY.JP は開業届がなければ確定申告書の控えや個人事業税納付証明書で代替可。
- **[法務] 条件付き可（確信度 中）** — 幹事本人が自分の主催イベントの参加費を自分で受け取ること自体を禁ずる決済法規は見当たらない。規制の名宛人は「他人の間の資金移動を業として引き受ける者」＝運営者側。

**現実的に存在する選択肢は3つ。** (a) 幹事が個人事業主相当として PAY.JP / Square / PayPay オンライン加盟店になる、(b) 幹事が PayPal ビジネス／本人確認済みアカウントで受け取る（connpass が実運用している構造）、(c) 幹事の個人銀行口座（楽天銀行）＋電子決済等代行業経由の入出金明細照会。(c) だけが「非事業者のまま」を満たす。

### 論点2. 受取先と自動検知を両立できるか（個人PayPay維持可否）

**回答: 個人PayPayを維持したままの自動検知は、公開仕様では不可。**

- **[技術] 不可（確信度 中）** — PayPay for Developers の公開ドキュメントを探索した範囲で、個人間送金（P2P）・送金リクエスト・グループ支払いを扱うAPIプロダクトは見つからなかった。ただし**これは非存在の証明ではない**（§3-1 参照）。公式サイトマップは公開ドキュメントの完全な索引ではなく、cashback / get_user_payout_detail / direct_debit / user_notification など索引外の公開ドキュメントが実在する。いずれも加盟店起点の一方向APIで、受取側個人アカウントの入金を読む機能ではない。
- **[規約] 不可（確信度 中）** — PayPayの「グループ支払い」は PayPayアプリ内で完結し、外部アプリから作成・参照する手段は公式ヘルプに記載がない。受け取りリンクも送信者が金額を確定して作るもので、第三者が受取人宛に金額指定で発行する仕組みはない。
- **[法務] 該当なし** — そもそも技術・規約段階で閉じている。

**この二者択一をユーザーに明示する必要がある。** (α) 自動チェックを取るなら受取先を変える。(β) 個人PayPayを取るなら自動チェックを落とし、「アプリは名簿・金額管理＋PayPay送金導線、確認は幹事の手動」に縮退する。引継ぎ書はこの縮退案を「中心要件を満たさない」と明記しているので、(β) を採るならユーザーの明示的な同意が要る。

### 論点3. Stripe等への問い合わせが必要か

**回答: 必要。ただし「禁止だから不可」ではなく「承認可否を確かめる」ための照会。**

- **[規約] 未確定（確信度 高）** — Stripe の禁止業種に「ピアツーピアの送金」があるのは事実。ただし反証検証で **「禁止業種＝事前承認の余地なし」は誤り**と判明した。Stripe 公式FAQは「Stripe は、禁止および制限付き業種リストに掲載された事業であっても、事前の明示的な承認があれば対応できる場合があります」と述べ、恒久的に対象外なのは違法商材等に限るとしている。
- **新規に判明した決定的な項目（確信度 中／単一レンズ検証）** — Stripe の「管轄区域固有の禁止業種」の**日本**節に「**Stripe Connect 外での C2C サービス**」が明記されている（あわせて「個人への寄付」も）。これが正しければ、日本で C2C を扱うには Connect が必要条件になる。ところが Connect × PayPay は公開された実装経路がない（概要ページ「Connect のサポート: いいえ」、Connect 専用2ページに PayPay の節も `paypay_payments` ケイパビリティも不在、サポート表だけが「✓＋招待をリクエスト」）。**「日本ではConnect必須」と「PayPayはConnect非対応」が同時に成り立つなら、Stripe＋PayPayでC2C型を組む道は塞がっている。** 照会の最優先事項。
- **[技術] 可（確信度 高）** — Stripe 側の Webhook・冪等性・署名検証の仕様は完全に文書化されており、実装上の不明点はない。

### 論点4. 幹事の登録・本人確認・審査負担

**回答: これが最大のプロダクトリスク。ルートごとに負担が段違い。**

- **[規約] 確信度 高** — Square: 開業届または代替書類。PAY.JP: 開業届がなければ確定申告書控え／個人事業税納付証明書。PayPay: 本人確認書類＋住所確認書類＋店舗内外観写真（実店舗ルート）。KOMOJU: 非事業者は不可。Stripe: 「何を売っているか」「そのカテゴリーをサポートできるか」が審査対象で、売るものがない幹事は審査で止まる。
- **反証検証による訂正（確信度 中）** — 「PayPay加盟店＝実店舗のある法人・個人事業主のみ」は**実店舗QR決済ルートのFAQの記述**であり、オンライン決済ルート（`paypay.ne.jp/store-online/`）には実店舗要件の記載がなく、加盟店規約の「加盟店」定義にも実店舗要件・事業者要件は条文化されていない。実質的な障壁は実店舗の有無ではなく「BtoCの商取引であること」で、公式に「商取引ではない寄付や募金、投げ銭（チップ）など一部NG商材もございます」とされている。**飲み会の会費がこれに当たるかが go/no-go の分岐点**であり、PayPayへの事前照会が必須。
- **審査期間（確信度 低・未検証）** — PayPay実店舗1〜2週間＋利用開始まで1週間、オンライン2週間〜1カ月＋5営業日。LINEミニアプリ認証審査1〜2週間。

### 論点5. 費用と資金の責任（手数料、返金、紛争、入金時期）

**回答: 「幹事に満額がすぐ入る」は成立しない。企画段階で明示しないと期待値が破綻する。**

- **手数料（確信度 低〜中・大半が未検証）** — Stripe: カード3.6% / PayPay 3.98%（デジタルコンテンツ9.48%）/ コンビニ3.6%（最低¥120）/ 銀行振込1.5% / 不審請求申し立て¥1,500件。PayPay直接契約オンライン: 物販3.8% / デジタルコンテンツ10%。Peatix: 4.9%＋99円/枚＋振込210円（実質約10.9%）。connpass: 自社手数料0円（PayPal 3.6%＋40円）。Doorkeeper: 99円＋2.5%（＋Stripe手数料）。**PayPay/Kyash/LINE内PayPayの個人間送金は手数料0円**なので、決済事業者を通す本アプリは構造的にコスト不利。
- **入金タイミング（確信度 低・未検証）** — Stripe日本は日次入金不可・デフォルト手動・初期7暦日／以降4営業日。PayPay直接契約オンラインは月末入金（月1回）。**飲み会当日の立て替え問題は解消されない。** 幹事画面では「支払済み（決済完了）」と「入金予定」を別ステータスで出す。
- **手数料の転嫁（確信度 低・未検証）** — PayPay加盟店規約（オンライン決済用）第4条第3項が「商品等代金以外の金銭の支払いを請求すること」を禁止しているとの記録がある。事実なら参加者への手数料上乗せは規約抵触の恐れ。手数料は幹事負担か会費内包で設計する。
- **返金（確信度 中）** — PayPay公式Node SDK は "Currently we only support 1 refund per order."（1注文1回）。Stripe経由のPayPayは全額・一部返金可、返金期間365日、即時完了。**返金原資を運営者が保持する設計は採らない**（§6）。

### 論点6. 最初の配布形態（LINEミニアプリ）

**回答: 配布は可能。ただし「LINE内完結」は決済までは実現しないし、2026年夏以降 LINE 本体が正面から競合する。**

- **[技術] 可（確信度 高）** — LIFF 上のWebアプリとして実装。参加者識別は `liff.getIDToken()` をサーバーへ送り、`POST https://api.line.me/oauth2/v2.1/verify`（または自前JWT署名検証、あるいはアクセストークン経路）で検証する。userId はプロバイダー単位で共通なので、ミニアプリチャネルと Messaging API チャネルは同一プロバイダー配下に置く（後から移せない）。
- **[規約] 条件付き可（確信度 高）** — 公式の決済表は日本について「LINE Pay ❌ / アプリ内課金 ✅ / その他の決済方法 ✅」。その他の決済方法は「一般のウェブページで決済を提供して処理するのと同様に実装してください」とされ、外部決済への遷移はブロックされない。ただし「外部のドメインや外部のアプリで決済を完了した後、ユーザーがLINEミニアプリのページに戻るようにしてください」という復帰要件がある。
- **未認証／認証済の分岐（確信度 高）** — 決済・カスタムアクションボタン・友だち追加誘導・広告掲載は未認証でも可。サービスメッセージ・Custom Path・ホーム画面ショートカット・共通プロフィールのクイック入力・ヘッダーへのアプリ名表示は認証済のみ。**外部決済で完結するMVPは未認証で本番リリースできる。** 支払完了通知（サービスメッセージ）、LINE内検索、ホームタブ掲載が必要になった時点で認証審査が前提になる。
- **運営主体（確信度 高）** — 認証済ミニアプリを出せるのは「日本の法人番号がある組織」または「日本の個人事業主」。NonTurn LLC は法人なので可。一般個人の幹事は**未認証ミニアプリなら自分名義で作れる**が、認証済は不可。したがって「幹事ごとに認証済ミニアプリを配る」構成は成立しない。
- **審査リスク（確信度 高）** — ポリシーの禁止業種に「募金、寄附、クラウドファンディング等の資金調達」、禁止事項に「チャリティまたは募金として寄付金を収集する目的の内容」がある。サービス定義を「幹事が管理する精算・集金の台帳」に統一し、寄付・募金・クラファンの文脈を排する。認証審査申請前の事前照会が要る。
- **市場前提の変化（確信度 低・未検証だが複数レポートで一致）** — LINEヤフーは 2026年7月2日、2026年夏以降に LINE と PayPay のアカウント連携を開始し、**LINEのトーク上でPayPay残高の送金と「グループ支払い」による割り勘**が使えるようになると発表。LINEミニアプリ版PayPay（残高確認・送受金・取引履歴・ATMチャージ。決済とポイント運用は除く）も提供予定。**本アプリの中核体験がプラットフォーム本体機能になる。** 差別化は送金そのものではなく、名簿・複数イベント横断台帳・21名以上・催促に置くしかない。

## 2. 資金フロー候補の比較

「運営者が資金に触れるか」が法務上の最重要軸。ここを触れる設計にした瞬間、資金移動業の論点が確定的に立つ。

|---|---|---|---|---|---|---|---|---|
| A | 幹事＝PayPayオンライン加盟店 | 幹事の加盟店売上→指定口座 | 触れない | Webhook(COMPLETED)＋`GET /v2/codes/payments/{id}`＋日次突合CSV | 高（審査2週〜1カ月＋5営業日、事業実態の証憑） | 物販3.8%／デジタル10% | 低（運営者が資金に入らない限り） | PayPay: 会費がBtoC商取引に当たるか |

### 候補別の補足

**A（PayPayオンライン加盟店）** — 当初希望「PayPayで受け取る」に最も近い。ただし受取先は個人PayPay残高ではなく加盟店売上で、入金は月1回。反証検証により「オンライン決済ルートには実店舗要件がない」ことが判明したため、当初の「非事業者は門前払い」という評価は緩む。真の障壁は NG商材判定。**照会1本で go/no-go が決まる最短経路。**

**B（Stripe）** — 技術資料が最も充実しており実装は素直。ただし規約が三重に立ちはだかる: SSA 1.2(a)(i)「personal, family, or household purposes」の包括禁止（幹事がStripeユーザーになる設計のとき）、禁止業種「ピアツーピアの送金」、日本固有「Stripe Connect 外での C2C サービス」。PayPay を決済手段に足す場合、Connect の可否が未解決のまま。

**C（PAY.JP）** — 必要書類が最も軽く、Webhook 仕様も明快。加盟店規約本文が未取得なので、個人間送金・立替精算の扱いを採用前に確認する必要がある。

**D（PayPal / connpass型）** — connpass が実運用している実在の前例。「運営者が資金を持たない／主催者の決済アカウントへ即時着金」という構造をそのまま模倣でき、法的論点の大半を回避できる。PayPal のビジネスアカウント要否とAPI資格が未確認（一次資料の取得に失敗）。

**E（銀行明細ルート）** — **「非事業者の幹事が受取人のまま自動検知できる」唯一の実在経路。** 楽天銀行APIサービス利用規定が個人口座に対し「口座情報照会、残高照会、入出金明細照会、振込結果照会、振込」を認めている。制約: (1) 利用には「外部サービス会社」＝電子決済等代行業者との契約が必須で、運営者が財務局登録を取るか登録済み事業者と組む、(2) 電代業登録は個人でも可だが事前相談→ドラフト提出→事前審査→正式申請でリードタイムが長い、(3) 着金ベースなので即時性が決済Webhookに劣る、(4) 振込依頼人名は参加者が書き換えられるため誤照合が起きる。**照合信頼度スコアと幹事の承認/却下UIを最初から入れる前提。**

**F（収納代行）** — MVPで選べる選択肢ではない。資金移動業の登録は株式会社でなければ取得できず（合同会社のNonTurn LLCは組織変更が前提）、最低要履行保証額の供託・体制整備が要る。ただし反証検証により **「運営者が資金に触れたら必ず登録が必要」は言い過ぎ**と判明した（§3-4）。内閣府令1条の2第3号ニは「銀行等又は資金移動業者からの委託」を除外要素として明文化しており、**登録済みの資金移動業者・銀行の委託先として構成する道が条文上開かれている。** これは新たに浮上した選択肢だが、提携先の確保が前提であり、初期スコープには入らない。

**G（決済連動なし）** — 引継ぎ書が「中心要件を満たさない」と釘を刺した案。ただし手数料ゼロ、PayPayの20名制限を超えられる、法的論点が消える、という利点は客観的に大きい。**採用するならユーザーの明示的な同意が要る。**

## 3. 反証で訂正された主張と、訂正後の表現

3レンズ反証検証（source / recency / inference）で覆った、または重要な限定が付いた主張。過去AIの断定の訂正を含む。

### 3-1. 【訂正】PayPayの公開APIプロダクトは「9種類に限られる」ではない

- **訂正前（PP-01, 3レンズ全てが refuted）**: 「PayPay for Developers の全プロダクトは加盟店決済向けのみ。公式サイトマップに列挙された9種類が全て」
- **訂正後**: サイトマップに9本のドキュメントURLが列挙されているのは事実だが、**サイトマップは公開ドキュメントの完全な索引ではない**。開発者ポータルのJSバンドルが参照する `@OPAAPIDocs` マップには cashback / direct_debit が含まれ、`www.paypay.ne.jp/opa/doc/` 配下には cashback（PayPayポイントAPI、`POST /v2/cashback`「ユーザーに残高の付与」）、get_user_payout_detail（ユーザー銀行口座への出金情報取得）、user_notification（プッシュ通知。決済APIではない）、account_link、paypay_card、get_public_key を含む計13本以上がHTTP 200で公開されている。したがって「全プロダクトが加盟店決済向け」も誤り（cashback は加盟店→ユーザーへの付与＝資金がユーザー側へ向かう）。
- **維持される結論**: 個人対個人（P2P）の送金API・送金リクエストAPI・グループ支払いAPIは、取得できた全ドキュメントを通じて見つからなかった。全プロダクトが加盟店登録（api key/secret の発行、手動審査、契約）を前提としている。**「幹事の個人PayPay着金をアプリが自動検知する設計は公開APIでは組めない」という運用上の結論は維持されるが、その根拠をサイトマップの列挙に置いてはならない。** 引継ぎ書§4-1 は「公開範囲にP2P送金/送金リクエスト/グループ支払いのAPIは存在しない」という限定形で扱い、確定させるなら PayPay 加盟店窓口への直接照会という別の一次根拠を取る。
- **付随して判明**: 継続課金と支払リクエストには「法人のお客様のみご利用いただけます」の明記があり、個人事業主での利用可否は別途確認が必要。

### 3-2. 【訂正】PayPay公式Node SDK は13メソッドではなく27メソッド

- **訂正前（PP-02, 3レンズ全てが refuted）**: 「SDKが実装するAPIはQR決済系8＋ネイティブ決済系5に限られる」
- **訂正後**: これはREADMEの記載範囲であり、実装（`src/index.ts` / `src/lib/paypay-rest-sdk.ts`）は27の公開メソッドを持つ。未記載分は PaymentPreauthorize / CheckUserWalletBalance / Authorization / AuthorizationResult / CreateSubscriptionPayment / CreatePendingPayment / GetPendingPaymentDetails / CancelPendingOrder / RefundPendingPayment / GetUserAuthorizationStatus / CashBack / CheckCashBackDetails / ReversalCashBack / CheckCashBackReversalDetails の14個。README自体にPayPayの注記「SDKのメンテナンスは限定的で、新機能はAPIレベルで直接追加される」がある。
- **維持される結論**: 27メソッドを精査してもP2P送金はない。ただし **「公式SDKにもP2P機能がないことで2系統の一次資料が一致する」という補強論法は使えない。** Node SDK は OPA ドキュメント記載エンドポイントの薄いラッパーであり、同一仕様の二形態にすぎず独立した2系統ではない。

### 3-3. 【訂正】Stripeの禁止業種は「事前承認の余地がない区分」ではない

- **訂正前（F02, 2レンズが refuted）**: 「ピアツーピアの送金は禁止業種であり、事前承認の余地がない区分に置かれている」
- **訂正後**: 列挙位置は正しい（禁止業種→金融商品およびサービス、Last updated 2026-09-22）。しかし Stripe 公式サポートFAQは「Stripe は、禁止および制限付き業種リストに掲載された事業であっても、**事前の明示的な承認があれば対応できる場合があります**。違法な商品・サービス等の一部区分は恒久的に対象外」と明記している。ピアツーピア送金は恒久的対象外区分には含まれない。
- **実務上の帰結**: 「Stripeは使えない」ではなく「**無条件の前提にはできない。事業モデルを開示して明示的承認を得られるかを確認する工程が要る**」。引継ぎ書 §4-2 の警戒自体は妥当だが、「承認の余地なし」と書いている部分があれば訂正する。

### 3-4. 【訂正・最重要】資金決済法2条の2の除外は「現金手渡しのみ」ではない

- **訂正前（F1, 3レンズ全てが refuted）**: 「2条の2は…受取人が個人であるものを為替取引とする。現金手渡しのみが除外される」「運営者が受入れ・引渡しのどちらにも関与しない構成を取らない限り登録必須」
- **訂正後**: 柱書が現金手渡しを除外するのは正しいが、**除外はそれだけではない**。第1号は「その他の内閣府令で定める要件」に委任しており、資金移動業者に関する内閣府令1条の2（現行・2026-06-01施行）が該当類型を3つに限定している。
  - 第1号 = 資金受入時までに債務者の債務が消滅しないもの
  - 第2号 = 信用供与（貸付・連帯債務者の一人としてする弁済＝立替払）により発生した債権の回収
  - 第3号 = イ〜ニの**いずれにも該当すること**（イ: エスクロー型でない／ロ: 契約成立に不可欠な関与を行うプラットフォーム型でない／ハ: イ・ロ該当者からの委託でない／ニ: **銀行等又は資金移動業者からの委託でない**）
- **設計上の帰結（最重要）**: 第3号はイ〜ニの全部充足を要するので、**イ・ロ・ハ・ニのどれか1つを崩せば第3号は不成立**になる。したがって「第3号ロ（プラットフォーム型）が唯一の設計上の選択肢」という整理は誤り。実務上は **ニ（登録済みの銀行等・資金移動業者からの委託先として構成する）が最も現実的な回避経路**として条文上明示されている。また出口も資金移動業登録に限られず、銀行免許、登録済み資金移動業者の委託先という選択肢がある。
- **同時に成り立つ制約**: 第1号・第2号は第3号と独立に判定される。「参加者が支払った時点で幹事への債務が消滅する」と規約に書いて第1号を外しても、**素の収納代行は第3号で捕捉される**。第1号を外すだけでは足りない。

### 3-5. 【限定】内閣府令1条の2の要約に2箇所の不正確

- **訂正前（F2, 2レンズが refuted）**: 「ハ＝他の収納代行業者からの受託でない／ニ＝銀行等からの受託でない」
- **訂正後**: ハは「**イ又はロの要件に該当しない者**（＝エスクロー型／プラットフォーム型の資金移動行為を行う者）からの委託等でないこと」で、一般の収納代行業者からの受託一般を指すのではない。ニは「銀行等**又は資金移動業者**からの委託その他これに類する方法によるものでないこと」で、資金移動業者が落ちていた。この2語の欠落が §3-4 の設計選択肢を見落とさせていた。

### 3-6. 【限定】内閣府令1条の2の「割り勘アプリ条項」— 第1号回避だけでは逃げられない

- **訂正前（F02/alt-providers の含意）**: 「決済成立と同時に参加者の債務が消滅し運営者が資金を持たない設計にすれば、この号の適用を避けられる」
- **訂正後**: 第1号を外すだけでは不十分。第3号が残余包括要件として素の個人向け収納代行を捕捉する。2019年12月の金融審議会WG報告が割り勘アプリの規制理由として挙げたのは「サービス提供者は個人間の債権債務関係の**発生事由に関与しておらず**、単に資金のやり取りを仲介しているだけ」であり、これは第3号ロ（契約成立への不可欠な関与）の不存在を指す。債務消滅のタイミングとは別軸。
- **維持される結論**: 適法ルートは (a) 柱書の外に出る（運営者が資金の受入れ・引渡しに関与しない）、(b) 第3号ニ（銀行等・資金移動業者の委託先）、(c) 第3号ロ（契約成立に不可欠な関与を伴うプラットフォーム）、(d) 自ら登録する、のいずれか。**規約の文言だけで外せるという説明は誤り。**

### 3-7. 【訂正】「LINE単体の送金/割り勘機能はもう存在しない」は誤り

- **訂正前（F04, 3レンズ全てが refuted）**: 「LINE Payは2025年4月30日に終了。LINE単体の送金/割り勘機能はもう存在しない」
- **訂正後**: LINE Pay の国内終了（2025-04-30、2024-06-13発表、PayPayへの一本化）は正しい。しかし**LINE内の送金/割り勘機能は現存する**。2024年10月15日以降、LINEのトークルームの「+」メニューからPayPayの「送る・受け取る」が手数料無料で使え（ID連携不要）、グループトークでは均等割りの支払いリクエストが送れる。さらに2026年7月2日発表のLINE×PayPayアカウント連携（2026年夏以降順次）では、PayPayアプリを介さずLINEのトーク上でPayPay残高の送金と「グループ支払い」による割り勘ができるようになる。
- **本アプリに残る客観的な隙間**: グループトークでは「**同じ金額の請求のみ対応可能**」という制約が一次資料で確認されている。参加者ごとに金額が異なる集金はLINEのグループトーク内で完結しない。これが「LINE内完結」軸で残る唯一の検証可能な隙間。
- **ただし**: LINEミニアプリ版PayPayについて PayPay 側の英文リリースは「決済およびポイント運用機能は現時点で非対応」と明記。完結しないのは個人間送金ではなく加盟店決済の方。

### 3-8. 【訂正】Stripeの「決済ファシリテーション」への当てはめは文言上そのままではない

- **訂正前（F03, 3レンズ全てが refuted）**: 「運営者が参加者から資金を受け取り幹事へ渡す構成は、制限業種『決済ファシリテーションおよびアグリゲーション』の定義に文言上そのまま当たる」
- **訂正後**: 当該定義は「サードパーティーの**売り手**」の「商品やサービスの**決済売上金**」を要件とする。割り勘の幹事は売り手ではなく、受領額も売上金ではないため、あてはめには解釈を要する。**より直接に当たるのは同ページの禁止業種「ピアツーピアの送金」**であり、さらに**「管轄区域固有の禁止業種」の日本節に「Stripe Connect 外での C2C サービス」が明記されている**（recency レンズが実取得して報告）。
- **帰結**: 日本でこの種のサービスを Stripe で組むなら Connect が必要条件として位置づけられている可能性が高い一方、Connect × PayPay には公開された実装経路がない。**この2点の衝突が Stripe 採用の最大の障害**であり、Stripe への照会事項の筆頭。
- **もう一点の訂正**: Stripe 自身がマーケットプレイス（プラットフォームが集金して売り手へ支払う）を Connect の推奨構成として公式文書化しており、必要手続きはダッシュボード上のセルフサーブ審査。「制限業種としての別建ての事前承認申請が実装着手の前提工程になる」という整理は公開文書から裏付けられない。

### 3-9. 【限定】Stripe SSA 1.2(a)(i) の射程

- **維持（F01, 2レンズが survived）**: SSA General Terms（Last modified 2025-11-18）§1.2(a)(i) に "use the Services for personal, family, or household purposes" が逐語で存在し、禁止業種条項 §1.2(a)(ix) とは独立した包括禁止。§1.1 は "User must use the Services solely for User's Business Purposes" と積極的に義務づける。日本向け Regional Terms は準拠法と紛争解決のみで 1.2 を変更しない。
- **限定（inference レンズが refuted）**: この条項が拘束するのは **Stripeアカウント保有者（User）** である。プラットフォーム自身が加盟店（merchant of record）となり幹事がStripeユーザーにならない設計では、1.2(a)(i) は幹事に直接適用されない（代わりに資金決済法の論点と、プラットフォーム側のP2P判定が主戦場になる）。また **幹事を個人事業主にしても十分条件にならない** — 資金の流れが友人間の集金と分配である限り (ix) のP2P禁止に独立に抵触する。
- **正しい問いの立て方**: 「幹事を個人事業主にするか」ではなく「**誰が加盟店になり、資金の流れがP2P送金と判定されない構造にできるか（対価性のある役務提供の実態があるか）**」。

### 3-10. 【限定】LINEミニアプリ「決済システムの利用は未認証でも✅」の意味

- **維持（LMA-02, 2レンズが survived）**: 機能差表の9行は一次資料と逐語一致。
- **限定**: 「決済システムの利用 ✅」が意味するのは、日本では実質「その他の決済方法」（外部決済）のみ。日本国内のLINE Payは終了済みで、LINEが提供する決済機構はアプリ内課金だけだが、アプリ内課金は「実際にユーザーが利用できるのは**認証済ミニアプリのみ**」（未認証では開発用・審査用でしか動作しない）、加えてコンソールからの利用申請と承認、消耗型デジタルコンテンツ限定、提供地域・事業者所在地とも日本限定。
- **帰結**: 外部決済で完結するMVPは未認証で本番リリースできる。認証審査が必要になるトリガーはサービスメッセージだけでなく、アプリ内課金・LINE内検索/ホームタブ掲載・Custom Path・ホーム画面ショートカットも同様。
- **付随**: 「広告の掲載」も未認証で可だが提供地域が日本であることが条件で、2026年10月14日のポリシー改定で利用可能な広告ネットワークが原則LINEヤフー広告ネットワークに限定されると予告されている（施行前・原文未確認）。

### 3-11. 【限定】「幹事が自分のミニアプリを持つ構成は成立しない」は認証済に限った話

- **維持（LMA-03, 2レンズが survived）**: 認証済ミニアプリの利用対象者は「日本の法人番号、または台湾やタイの納税番号がある組織」「日本の個人事業主」。ポリシー最終改定 2026年2月19日。
- **限定（inference レンズが refuted）**: 同じポリシーが未認証ミニアプリの対象者に「日本、台湾およびタイの**個人**」を挙げている。一般個人の幹事でも未認証ミニアプリは自分名義で作れる（認証バッジなし、ヘッダーにドメイン名表示、LINE検索・ホームタブ非掲載、ショートカット・Custom Path不可）。
- **もう一点の限定**: 「NonTurn LLC が単一ミニアプリを運営する構成が唯一で、これは資金移動業の論点を**必ず**呼び込む」は誤り。論点を呼び込むのは運営主体が単一であることではなく、**運営者が資金を預かるか否かという独立した設計選択**。

### 3-12. 【限定】PayPay加盟店決済の「自動チェックは技術的に確実」

- **維持（PP-03, 2レンズが survived）**: `GET /v2/codes/payments/{merchantPaymentId}`、Webhook（AUTHORIZED / COMPLETED / CANCELED / EXPIRED / EXPIRED_USER_CONFIRMATION / FAILED ＋ file.created）、Sandbox（`apigw.sandbox.paypay.ne.jp`）はいずれも公式ドキュメントに実在。merchantPaymentId は最大64文字・`[a-zA-Z0-9_-]` なので「イベントID＋参加者ID」の埋め込みは可能。
- **限定（inference レンズが refuted）**: (1) OPA を使えるのは事業者として情報提出・手動審査・契約締結を経てオンボーディングを完了した "payment partner" に限られ、API キー／シークレットと Webhook エンドポイントは PayPay 側が設定する。Webhook 登録はマーチャントパネルまたは営業担当経由でセルフサービスではない。**加盟店であることと OPA・Webhook を使えることは別。** (2) 決済詳細レスポンスに支払者を識別するフィールドがない。取得できるのは「**どの決済リクエストが支払われたか**」までで「誰が支払ったか」ではない。参加者ごとに個別QR/リンクを配る運用を前提にすれば実務上の突合は可能だが、**代理支払いや取り違えをAPI側で検知することはできない**。
- **設計への反映**: 引継ぎ書§7の「代理払いを追える」という要件は、決済事業者のAPIだけでは満たせない。アプリ側で「この請求は誰宛に発行したか」を持ち、代理払いは幹事が手動でマークする導線を用意する。

### 3-13. 【限定】Webhook 冪等性は event_id の一意制約だけでは足りない

- **維持（T8, 2レンズが survived）**: Stripe はイベントの配信順序を保証せず、同一イベントが複数回届きうる。`created` を順序判定・処理済み判定に使わずイベントIDを追跡せよと公式に指示。本番は指数バックオフで最長3日リトライ。
- **限定**: 同じページが「場合によっては、2つの Event オブジェクトが個別に生成・送信されます。これらの重複を識別するには、`data.object` のオブジェクトIDと `event.type` を使用します」と明記している。**`(provider, event_id)` の一意制約は必要条件だが十分条件ではない。** 別IDの重複イベントに備え、`(data.object のID, event.type)` を鍵にした業務レベルの冪等キーを併用する。
- **もう一点**: 「この2点がないと二重加算と状態巻き戻りが必ず起きる」は言い過ぎ。状態更新が代入的に冪等（status を 'paid' に設定）なら二重加算は起きない。導けるのは「重複配信と順不同に耐える冪等な処理」と「支払状態が後退しない更新規律」という2つの**性質要件**まで。

### 3-14. 【限定】LINE IDトークンのサーバー検証経路は1つではない

- **維持（T4, 2レンズが survived）**: LINE は `liff.getDecodedIDToken()` / `liff.getProfile()` で得たプロフィール情報をサーバーへ送ることを禁じ、IDトークンまたはアクセストークンを送ってサーバー側で検証するよう指示。`POST https://api.line.me/oauth2/v2.1/verify` は `id_token` と `client_id` が必須。
- **限定**: 公式に認められた経路は3つある。(a) 上記の verify エンドポイント、(b) IDトークンのJWT署名を自前検証（LIFFはES256＋JWKS、WebログインはチャネルシークレットのHS256）、(c) アクセストークンを `GET /oauth2/v2.1/verify` で検証し `GET /v2/profile` を叩く。「必ず verify エンドポイントを経由する」という限定は正しくない。
- **無条件に成立する核心**: フロントエンドから送られたユーザーIDを信用して支払済みフラグを立ててはならない。
- **実装上の精度**: `client_id` は LINE Login チャネルID（LIFF ID や Messaging API チャネルIDではない）。

### 3-15. 【限定】PayPay加盟店資格「実店舗のある法人・個人事業主」の射程

- **維持（F05, 2レンズが survived）**: 実店舗向けQR決済の店舗オーナー向けFAQに「実店舗のある法人様・個人事業主様であれば、どなたでもお申込みいただけます」が逐語で存在。事業者でない一般個人を対象に含める記述はない。
- **限定（inference レンズが refuted）**: これは**実店舗QR決済ルートの業種制限の回答**であり、PayPay加盟店全体の申込資格ではない。同FAQ自身が非対面決済について「オンライン決済のお申込みが必要となります」と別ルートを案内し、`paypay.ne.jp/store-online/` には実店舗要件の記載がない。加盟店規約第1条の「加盟店」定義にも実店舗要件・事業者要件は条文化されていない（個人事業主の存在は第20条3項で前提とされている）。「実店舗」要件自体も、移動販売・キッチンカー・フリーマーケット出店・開業前の申込が可能とされており字義ほど厳格ではない。
- **真の障壁**: (a) 加盟店規約が決済対象を「加盟店が販売する商品もしくは権利または提供する役務」の代価に限定している、(b) オンライン決済が「BtoCの商取引」を対象とし、商取引ではない寄付・募金・投げ銭を除外している。**立替金の精算はこの審査基準に適合しない可能性が高い。**
- **もう一点の限定**: 「受取先＝幹事の個人PayPay」自体は個人間送金として規約上開かれている。閉じているのは**プログラムによる自動照合の手段だけ**。したがって選択肢は二択ではなく、①幹事個人受取を維持し照合をアプリ外（手動・自己申告）に置く、②受取先を運営事業者名義に変える、③受取先を幹事名義の銀行口座に変えて入出金明細から照合する、の複数がある。

## 7. 「自動チェック要件を完全に満たせる正規経路は存在するか」への回答

### 7-1. 結論: **条件付きで存在する。無条件では存在しない。**

引継ぎ書の中心要件を分解すると3つの条件がある。

1. 参加者ごとに支払いを検知できる
2. 受取先が幹事の個人PayPay
3. 幹事が一般個人（非事業者）のまま使える

**この3つを同時に満たす経路は、一次資料の範囲では存在しない。** 条件2を落とすか、条件3を落とすかで、経路が生まれる。

| 落とす条件 | 生まれる経路 | 確信度 |
|---|---|---|
| 条件3を落とす（幹事が個人事業主相当になる） | 候補A（PayPayオンライン加盟店）／C（PAY.JP）／D（PayPal）／B（Stripe） | 中 |
| 条件2を落とす（受取先を幹事の個人銀行口座に変える） | 候補E（楽天銀行＋電代業経由の入出金明細照会） | 中 |
| 条件1を落とす（自動チェックを諦める） | 候補G（名簿＋PayPay送金導線＋手動確認） | 高 |

### 7-2. なぜ「無条件では存在しない」と言えるか（根拠の格付け）

- **PayPay側**: 公開ドキュメントを探索した範囲でP2P送金・送金リクエスト・グループ支払いのAPIは見つからず、全プロダクトが加盟店登録を前提としている。**ただしこれは非存在の証明ではない**（サイトマップが完全な索引でないことが反証検証で判明したため、「網羅的に探した」とは言えない）。確定させるにはPayPay窓口への照会が必要。→ **確信度 中**
- **API/Webhookを提供する主体は例外なく加盟店／ビジネスアカウント**であり、加盟店登録には事業実態の証憑が要る（KOMOJU は非事業者を明示的に排除、Square は開業届または代替書類、PAY.JP は確定申告書控え等）。→ **確信度 高**
- **個人向けの送金インフラ**（PayPay送る・受け取る、ことら送金）には第三者アプリ向けの公開照会APIが存在しない。ことらについては「公式サイトに記載がない」の確認に留まる。→ **確信度 中**
- **例外**: 楽天銀行が個人口座に対して入出金明細照会APIを提供している。これが唯一「非事業者の個人が受取人のまま自動検知できる」実在の経路。ただし電子決済等代行業の登録または登録済み事業者との提携が前提。→ **確信度 中**

### 7-3. 満たせない場合、何をどう明示して代替を提示すべきか

**ユーザーに提示すべき事実（順序も含めてこの通りに）**

1. **「幹事の個人PayPayで受け取る」と「自動で支払済みチェックが付く」は、PayPayの公開仕様では両立しません。** どちらを優先するかを決めていただく必要があります。
2. **理由は2段階です。** (a) 個人のPayPayアカウントに届いた送金を第三者アプリが照会するAPIが公開されていない。(b) 自動照合ができるのは加盟店決済だけで、加盟店になるには事業実態の書類が要る（そして会費徴収が取扱可能商材に当たるかはPayPayに確認が必要）。
3. **さらに、受取先を変えても解決しない問題が2つあります。** (a) 決済事業者を通すと手数料が乗る（3.6〜3.98%程度。5,000円の会費で180〜200円）。PayPayやKyashの個人間送金は手数料0円なので、無料の既存機能より高くなります。(b) 決済完了と幹事への入金は別物で、最大1カ月ずれます（PayPay直接契約は月末入金月1回、Stripe日本は日次入金不可でデフォルト手動）。飲み会当日の立て替え問題は解消しません。
4. **加えて、2026年夏以降にLINE本体がこの体験を提供します。** LINEヤフーは2026年7月2日、LINEのトーク上でPayPay残高の送金と「グループ支払い」による割り勘ができるようになると発表しています。純粋な送金・割り勘では勝負にならないので、差別化を台帳側（参加者名簿、複数イベント横断、21名以上、催促、領収記録）に寄せる必要があります。

**提示すべき代替案（推奨順）**

- **代替1（推奨・自動チェックを維持）**: 受取先を幹事の決済アカウント（PayPayオンライン加盟店／PAY.JP／PayPal）に変える。ターゲットを「飲み会の幹事」から「サークル・部活・教室・コミュニティの継続的な主催者」に寄せる。connpass / Doorkeeper が実運用している「運営者は資金に触れず、主催者の決済アカウントへ直接入金」構造をそのまま模倣する。**着手条件: PayPayへの商材照会1本。**
- **代替2（自動チェックを維持・非事業者のまま）**: 受取先を幹事の楽天銀行個人口座にし、振込依頼人名に識別子を載せて入出金明細照会APIで突合する。運営者が電子決済等代行業の登録を取るか登録済み事業者と提携する。**検知は着金ベースで即時性が劣り、振込依頼人名は参加者が書き換えられるため誤照合が起きる。** 照合信頼度スコアと幹事の承認／却下UIを最初から入れる。**着手条件: 電代業のリードタイムと提携先の確保。**
- **代替3（自動チェックを2段階に分ける）**: 「決済Webhook由来の即時確定」と「銀行明細由来の遅延確定（照合信頼度付き）」を同じ台帳の上に並べ、幹事が受取手段を選べるようにする。PaymentProvider アダプタと同じ層に BankReconciler を置く。手数料ゼロの経路と自動化された経路を共存させられる。
- **代替4（自動チェックを落とす・要ユーザー同意）**: アプリは名簿・金額・イベント管理に徹し、送金はPayPayの個人間送金（手数料0円）へリンクで導線を作り、支払済みチェックは幹事が手動で付ける。**引継ぎ書が「中心要件を満たさない」と明記した案なので、これを『自動チェック要件を満たした』と説明してはならない。** ただし手数料ゼロ・PayPayの20名制限を超えられる・法的論点が消えるという利点は客観的に大きい。

**絶対にやってはいけない代替の説明の仕方**

- 自己申告やスクリーンショットを「検証済み入金」として扱う
- 手動チェック版を作って「自動チェック要件を満たした」と説明する
- 名称だけを「参加費」「商品代金」に変えて、実態が個人間の立替精算のまま決済事業者を通す
- 「Connect を使えば運営者は資金を預からないから資金移動関連の法的検討は不要」と結論づける
