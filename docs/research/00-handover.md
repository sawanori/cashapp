# 幹事向け会費集金アプリ｜AI引継ぎ書（ユーザー提供・原文）

作成日：2026年9月24日（日本時間）
対象：本スレッドでの企画相談
現在の段階：要件整理・実現可能性の検討。会話内では、決済事業者の承認取得、技術選定の確定、実装、本番決済テストは行っていない。

> **最重要事項**
> 作りたいのは「参加者リストがあり、参加者の支払いを検知すると、その人に自動で支払済みチェックが付くアプリ」。当初の受取先の希望は「幹事の個人PayPay」。PayPay以外のモバイル決済も検討可能。
> ただし、これまでのAIの説明には、Stripe／Stripe Connectでの実現可能性について断定しすぎた部分がある。本書の「確認結果・訂正」を優先し、過去の提案を実装可能な確定仕様として扱わないこと。

## 3. 実現したい体験（暫定フロー）
幹事が集金対象のイベントを作る → 参加者名と請求額を登録 → 各参加者が自分に対応する支払い画面を開く → 参加者が支払う → 決済事業者の正規の通知／照会手段で成功を確認 → 該当参加者の支払状況を自動更新 → 幹事の参加者リストに「支払済み」チェック。

幹事画面（説明用仮データ）：田中 5,000円 ✅ / 佐藤 5,000円 ✅ / 山田 5,000円 未払い / 鈴木 5,000円 未払い。支払済み 2/4 人、10,000円/20,000円。

「決済完了」と「幹事への入金完了」は分ける。銀行口座への入金を使う構成では、参加者の決済成功と幹事口座への着金を同じ意味にしない。当初の希望は個人PayPayへの送金であり、銀行着金への変更は承認されていない。代替案を提示する際は受取先と受取時期の違いを明示する。

## 4. 決済に関する確認結果・過去の説明の訂正
### 4-1. 個人PayPayの送金を自作アプリで検知できるとは確認できていない
PayPay公式には個人間で残高を送る・受け取る機能がある。一方、確認した公式SDKの取引照会は加盟店が発行する merchantPaymentId を用いる決済向け。一般の個人PayPayアカウントに届く送金を第三者アプリから取得・照合する公開API／Webhookは、確認範囲では見つかっていない。実装可能な前提にしてはならない。PayPayへのリンクを開くことと、支払い完了をアプリが検証できることは別問題。自己申告やスクリーンショットを検証済み入金として扱わない。「PayPayで送金→参加者が申告→幹事が手動確認」は自動検知ができない場合の代替案であり中心要件を満たさない。

### 4-2. Stripeは個人間送金に自由に使えるサービスではない
Stripeの禁止・制限業種一覧では Peer-to-peer money transmission が禁止対象。「Stripe Connectを使えば誰でも幹事になって友人から会費を集められる」は断定しすぎ。実態が個人間送金・立替精算ならStripe採用を前提にしない。有料イベント等の対価モデルを検討する場合も、取引内容と受取人属性をStripeへ説明して適否を確認する。名称だけを「参加費」「商品代金」に変えて別物として扱わない。Connectを使うことだけを根拠に「運営者が資金を預からない」「資金移動関連の法的検討が不要」と結論づけない。

### 4-3. StripeのPayPay対応と、ConnectでのPayPay利用は別の確認事項
PayPay概要ページは Connect support: No。一方、決済方法対応表ではPayPayのConnect欄が対応扱いで「Connectでの利用には招待を申請する」脚注あり。公式資料間に記載差がある。断定せず、用途・アカウント構成・招待/審査条件をStripeに確認する。

### 4-4. ネイティブアプリ化と、決済手段の利用可否は別問題
SDKがあることは承認を意味しない。Webで使える決済手段がモバイルSDKで同様に使えると推定しない。「App Store審査的にも問題ない」も確認済みではない。

### 4-5. 手数料の説明は確定見積もりとして引き継がない
「参加者10人が5,000円払えば幹事に50,000円がそのまま入る」とは決めつけない。

## 5. 現在の選択肢の整理
| 方式 | 受取先・仕組み | 自動チェックに関する判断 |
|---|---|---|
| 個人PayPayへの送金を外部アプリから管理 | 当初の希望に近い | 入金を取得する正規APIが未確認。自動化可能と扱わない |
| PayPay公式のグループ支払いをそのまま利用 | PayPay内で管理 | 既存機能として比較可能。自作アプリへ取り込めることは未確認 |
| 加盟店決済としてのPayPay等 | 承認された事業者が対価を受領 | 取引状態の照会は可能でも、一般の幹事の個人送金とは別モデル |
| Stripe／Connect | 承認された取引・受取人 | 個人間送金の禁止と、PayPayのConnect利用条件が先に解決すべき点 |
| 他社の送金・銀行連携サービス | 今後の調査候補 | 日本の個人幹事を受取人にできることと入金通知APIの両方を確認。未発見・未選定 |

「誰が、何の対価または精算として、誰に支払い、どこで受け取るか」が成立していることを先に確かめる。

## 7. 最小構成と自動チェックの設計方針
最小構成：イベント作成、参加者登録、請求額設定、参加者ごとの支払い導線、支払い結果の取得、参加者一覧の自動更新、未払い人数・金額の表示。
自動更新フロー：請求レコード作成 → サーバー側で決済作成し請求IDと決済IDを関連付け → 参加者が支払う → Webhook受信／正式API照会 → 対象請求・受取先・金額・通貨・成功状態を確認 → 重複防止しつつ支払記録保存 → 一覧へ反映。
外さないこと：支払いの根拠（イベント名だけで判定せず payment_status 等を確認、遅延決済の後続通知）、安全な処理（署名検証、重複再送で二重加算しない、順序入れ替わり）、本人・請求の対応（識別子で結合、参加者側から金額・状態を書き換えられない、代理払いを追える）、例外と記録（失敗・キャンセル・二重払い・返金・遅延通知、更新履歴、イベント間で名簿が混ざらない、他人のPIIを見せない）。一覧更新は「決済事業者の確認後に反映」。

## 8. 類似サービス
PayPayのグループ支払い（メンバーへの請求、均等割り、個別調整、支払い状況確認）。Peatix、EventRegist、Splitwise は未再検証。「PayPayに勝てない」等は検証済み市場分析ではない。

## 9. 将来機能（必須ではない）
出欠管理、催促、プッシュ通知、当日QR受付、二次会追加徴収、複数集金方法の台帳、複数イベント管理。「手動チェック版」を作る場合も自動チェック要件を満たしたと説明しない。

## 10. 次に解くべき論点
1. 個人幹事向けの会費回収に使える正規サービスはあるか（友人間立替精算と、事業としてのイベント参加費を分ける）
2. 受取先と自動検知を両立できるか（個人PayPay維持可否。銀行受取へ勝手に変更しない）
3. Stripe等への問い合わせが必要か
4. 幹事の登録・本人確認・審査負担（一般個人が使えるか。個人事業主向けと混同しない）
5. 費用と資金の責任（手数料、返金、紛争、入金時期と責任者）
6. 最初の配布形態（今回：LINEミニアプリ）
