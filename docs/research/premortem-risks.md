## 0. 統合にあたっての裁定（レンズ間の矛盾と、重複の解消）

複数レンズが同じ欠陥に別方向の対策を出した箇所がある。後工程が迷わないよう、ここで一本化する。

| # | 対立 | 裁定 |
|---|---|---|
| A1 | line-platform は「復帰識別子を URL パスに置く（returnToken）」、data-infra は「招待トークンをパスから外す（ログ・Referer に残るため）」と主張した。 | **両立させる。** 恒久的な `joinToken` はパスから外しヘッダ／POST ボディで運ぶ。決済復帰の `return_token` は単回・15分・invoice 1件分しか返さない短命トークンなのでパス配置を許す。「長寿命の識別子はパスに置かない、単回・短命の識別子は置いてよい」を規約として明文化する。 |
| A2 | payment-integrity は「ゲート off でも Webhook 受信と返金は止めるな」、security は「Preview 環境では Webhook と cron を無条件 404 にせよ」と主張した。 | **レイヤを分ける。** 環境ガード（`VERCEL_ENV !== 'production'` なら 404）は最外層で常に効かせる。コンプライアンスゲート（`compliance_gate` / `feature_flag`）は `createCheckout` と `provider_binding` 作成だけを止め、受信・保存・照合・返金は止めない。設計ブリーフ §5-2 の「すべての入口に置く」は誤りであり、書き換える。 |
| A3 | security（SEC-11）は「金額不一致ならランクを前進させるな」、payment-integrity（PI-07）は「金額不一致でも受領の事実は台帳へ書け」と主張した。 | **両方採る。台帳（事実）と invoice（判断）を分離する。** 不一致でも `ledger_entry.kind='adjustment'` として受領事実を記録し、`invoice.settlement_rank` は動かさず `needs_attention=true` を立てる。ブリーフ §9-2 の C5「台帳に書かれない」は誤りであり、C20 に置き換える。 |
| A4 | security（SEC-02）の「参加者単位の claim トークン」と ux-adoption（UXA-10）の「参加者ごとの個別リンク」は同じ実装で満たせる。 | **1本の実装に統合する。** 幹事が参加者ごとに発行する一意トークン（`participant.claim_token_hash`、128ビットCSPRNG）を個別リンクの本体とし、グループ配布用の `joinToken` は名簿候補一覧の表示までしか権限を持たせない。 |
| A5 | data-infra（DI-12）は「追記専用を `CREATE RULE ... DO INSTEAD NOTHING` で守ると無言で0行になる」、security（SEC-04）は「REVOKE 先の `app_rw` ロールが存在しない」と指摘した。 | **両方が同じ穴の別側面である。** ランタイム接続を実在する最小権限ロール `app_rw` に切り替え、追記専用は RULE ではなく `BEFORE UPDATE/DELETE` トリガの `RAISE EXCEPTION` で強制する。「成功に見えて何も起きない」経路を残さない。 |
| A6 | ops-support（OPS-02）は「入金予定 UI を Phase 3 へ送れ」、payment-integrity（PI-12）は「payout テーブルを追加せよ」、ux-adoption（UXA-08）は「手数料を事前提示せよ」と主張した。 | **段階を分ける。** Phase 1–2 は `settled_at` と「入金予定」UI を実装せず、`settlementLagHint` と手数料概算・受取見込額の**事前提示**だけを必須にする（推定値であることを明示）。`payout` テーブルと `listSettlements` は Phase 3 に置く。 |
| A7 | ConformanceKit の追加ケース番号を4レンズが独立に C13〜C15 として提案し衝突した。gate-check の追加ルールも同様。 | **本書で一意に採番し直す。** ConformanceKit は C13〜C31、gate-check は G0 と G11〜G14 とする（§3 に記載）。 |

**統合で消えた重複の主なもの:** PEPPER ローテーション不能（4レンズが独立に指摘）、claim 解除手段の不在（3レンズ）、Preview 環境の本番接続（2レンズ）、outbox の配達先不在（2レンズ）、紛争・チャージバックの表現不能（3レンズ）、手数料・入金の不可視（3レンズ）。**同じ欠陥を4レンズが独立に見つけたという事実自体が、その欠陥の実在性を強く支持する。**

## 5. 「起きたら即停止」条件（決済機能のキルスイッチを引く条件）

### 5-1. 止める操作の定義（何を止め、何を止めないか）

**キルスイッチは「新規の資金移動」だけを止める。受信・保存・照合・返金は止めない。** これを取り違えると R-PAY-08 が起きる。

| レバー | 止まるもの | 止まらないもの |
|---|---|---|
| `PAYMENTS_ENABLED=false`（全体） | 全 provider の `createCheckout` と `provider_binding` 作成 | Webhook 受信と保存、`getPaymentStatus`、照合ジョブ、`refund`、`manual_confirm` |
| `PROVIDER_<KEY>_MODE=off`（provider 単位） | 当該 provider の `createCheckout` と接続 | 同上（当該 provider の既存 pending も照合を続ける） |
| Vercel Firewall のパス遮断 | 当該エンドポイントへの外部アクセス | アプリ内部の cron と照合 |
| `app_user.session_epoch` の一括インクリメント | 全セッション（再ログインが必要） | 台帳と照合 |
| `provider_binding.status='suspended'` | 当該幹事の自動決済 | 当該幹事の `manual_confirm` 運用 |

### 5-2. 即時に `PAYMENTS_ENABLED=false` を引く条件（人間の判断を待たない）

1. **法務ゲートの不正な通過を検知した。** `audit_log` に人間以外の actor による `gate.%` / `flag.%` の変更がある、または `docs/gates/*.json` と `compliance_gate` に差分がある。（R-OPS-09, R-SEC-06, R-SEC-07）
2. **弁護士から Q-LG1 に否定的な回答が出た**（為替取引に該当しうる）。（R-LAW-01）
3. **決済事業者から規約違反または加盟店資格に関する指摘を受けた。** クレデンシャル預託、取扱商材、虚偽申告、取引パターンのいずれでも。（R-LAW-02, R-LAW-03, R-LAW-04）
4. **`SUPABASE_SERVICE_ROLE_KEY`・PEPPER・セッション署名鍵のいずれかの漏洩が確認または強く疑われる。** ビルド成果物への混入検知、誤コミット、外部からの報告を含む。（R-SEC-04, R-SEC-09, R-SEC-13）
5. **Preview または非 production 環境から本番 DB への書き込みが確認された。**（R-SEC-05）
6. **監査連鎖の検証（`audit:verify`）が不一致を返し、改竄の可能性を否定できない。**（R-SEC-15）
7. **同一 invoice への過払い、または金額不一致で `paid` になった請求が1件でも確認された。**（R-PAY-02, R-PAY-04, R-PAY-13）
8. **LINEヤフーからミニアプリポリシー違反の指摘を受けた**（アプリ内課金条項を含む）。（R-LINE-05）

### 5-3. provider 単位で `off` に落とす条件

1. 当該 provider の `apply_result='mismatch'` または `'orphan'` が1日に5件以上発生した。（R-PAY-01, R-PAY-04）
2. 事業者照会が 429 を返した、または Webhook の受信レートがベースラインの10倍を超えた。（R-SEC-11）
3. `ProviderAccountError` が同一 binding で連続 N 回発生した（当該 binding のみ `suspended`）。（R-OPS-03）
4. アダプタの `parseWebhook` が本番ペイロードで例外を投げた（fixture が実物と乖離している）。（R-TH-07）
5. 当該 provider の必須ゲートが `valid_until` を過ぎて陳腐化した。（R-LAW-14）

### 5-4. 決済以外を止める条件

| 条件 | 止めるもの | 対応リスクID |
|---|---|---|
| 招待トークンの漏洩が確認された | 当該イベントの `join_token` をローテーションし旧トークンを失効。旧トークンでの claim を unclaim 候補として提示 | R-SEC-02, R-SEC-01 |
| セッション偽造または IDトークン再利用の兆候 | 当該ユーザーの `session_epoch` を進めて全セッション失効 | R-SEC-08 |
| XSS が確認された | 当該フィールドを一律エスケープ表示に落とし、全セッションを失効 | R-SEC-12 |
| `deepLink` に許可外ホストが登録された | 当該イベントの `manual_confirm` 導線を停止し、幹事を `suspended` に | R-SEC-14 |
| 悪用スコアが閾値を超えた | 当該幹事の新規イベント作成と招待リンク発行を停止 | R-LAW-10 |
| 催促のブロック率が閾値を超えた | 当該イベントの催促を自動停止 | R-LAW-15 |
| 未成年が含まれるイベント | 自動決済を提示せず `manual_confirm` に固定 | R-LAW-09 |
| 利用者数が未認証ミニアプリの上限に近づいた | 招待の新規発行を止め、既存イベントの完走だけを許す縮退モード | R-LINE-06 |
| 高 severity の未解決 concerns が3件以上 | 新規機能タスクの着手を停止 | R-TH-09 |
| コストが日次予算を超過 | Opus 呼び出しを停止し Gemini 単独スクリーニングへ縮退（縮退した事実を記録） | R-TH-10 |
| ハーネスのゲートが違反フィクスチャを落とせない | 全マージを停止しゲートを目視監査 | R-TH-01 |

### 5-5. 停止時に必ず行うこと

1. 停止したレバーと理由と時刻を `audit_log` と `docs/PROGRESS.md` の両方に記録する。
2. **照合ジョブと Webhook 受信は止まっていないことを `reconciliation_run` の新規行で確認する。** 止まっていれば R-PAY-08 の誤適用が起きている。
3. 幹事に `degraded` の告知帯で状況と復旧見込みを表示する。「支払いを止めています」と「入金の記録は続いています」を分けて書く。
4. 停止中に届いた `payment_event` を復旧後に適用し、`reconciliation_run.advanced` が期待どおり動いたことを確認する。
5. 復旧の判断は人間（noritaka）が行う。AI は停止はできるが再開はできない。

## 6. 本統合で検証していないこと（正直な申告）

- **本統合者は一次資料を1件も再取得していない。** 8レンズの出力と `design/synthesis.md`、`handover.md`、`local-context.md` のみを突き合わせた。法令の条文番号、決済事業者の規約文言、LINE ミニアプリポリシー、Vercel / Supabase の仕様は、各レンズの申告をそのまま引き継いでいる。
- **legal-compliance レンズと team-harness レンズは外部モデル（gemini-3.5-flash）を経由しており、Gemini CLI が 2026-06-18 に廃止済みで Antigravity バックエンドへ自動フォールバックし、指定モデルが適用されなかった旨がツール応答に記録されている。** この2レンズの出力は「指定したモデルによる検証」ではない。R-TH-11 はまさにこの事象そのものである。
- **severity と likelihood は各レンズの申告値を採用し、統合時は最も高い値に寄せた。** 独立した再評価は行っていない。統合で生じた S1 の総数（42件）は、設計ブリーフの未成熟さと同時に、8レンズが重複して同じ箇所を叩いたことの反映でもある。
- **本書に挙げた「先回り策」のうち、実装コストの見積もりを行ったものは1つもない。** すべてを Phase 1 に入れることは日程上おそらく不可能であり、どれを Phase 1 に入れどれを受容するかは PO の判断事項である。判断の出発点として、§1-1 の21件（S1×high）を Phase 1 の必須、§1-2 の21件（S1×medium）を Phase 1 完了条件、それ以外を Phase 2 以降とすることを推奨する。
