# ADR-009: LINE ID トークンの nonce 検証を採らず、単回使用テーブルで再利用を止める

- ステータス: accepted
- 日付: 2026-09-24
- 起票タスク: task_012
- 関連リスク: R-SEC-08（ID トークンの再利用）、R-SEC-10（鍵運用）、R-LINE-04（環境取り違え）
- 関連制約: N2、N3
- 関連チェック: check_005、check_072
- confidence: **高**（LINE の一次資料で裏が取れている。`docs/vendor-docs/line/verify.md`、取得日 2026-09-24）

---

## 背景

`docs/research/design-synthesis.md` §1-5 の手順②は ID トークンの検証項目として
「sub / aud / exp / **nonce** を検証」と書いていた。プレモータム R-SEC-08 は、この
「nonce を検証する」という記述にサーバー側で nonce を発行・保持する段取りが
一切対応していないことを指摘した。

一次資料（`docs/vendor-docs/line/verify.md` §1・§3）で確かめた事実:

- `POST https://api.line.me/oauth2/v2.1/verify` の `nonce` は **任意パラメータ**であり、
  その説明は "Expected `nonce` value. Use the `nonce` value provided in the authorization request"。
  つまり**認可リクエストを自分で組み立てた側**が、自分の発行した nonce を突き合わせるための口である。
- LIFF アプリで `liff.getIDToken()` が返すトークンは、LIFF の初期化時にプラットフォーム側が
  行った認可の結果である。認可リクエストはこちらが組み立てていない。
- `liff.login()` による認可リクエストは、LIFF ブラウザ内では**動作が保証されない**
  （`docs/research/research-line-miniapp.md` Q4）。つまり「`liff.login({ nonce })` で
  サーバー発行の nonce を渡す経路に作り替える」案は、本アプリの主経路（LIFF ブラウザ）で
  成立する保証がない。

この状態で `nonce` の検証を仕様に残すと、実装者は (a) 黙って省く、(b) 無意味な比較を書く、
のどちらかになる。どちらでも ID トークンは有効期間（発行から 1 時間）内なら何度でも
セッション発行に使えるベアラトークンのままである。

## 決定

1. **nonce 検証は採用しない。** `verify` へのリクエストに `nonce` を送らず、レスポンスの
   `nonce` も検証条件にしない。この判断の根拠は上記のとおり「サーバーが nonce を
   発行できる経路が LIFF ブラウザで保証されていない」ことであり、実装の手間ではない。
2. 代わりに **ID トークンを単回使用にする**。検証に成功した ID トークンの識別子を
   `used_id_token`（task_011 で作成済み）に保存し、2 回目の提示を 401 で拒否する。
   - 識別子: ペイロードに `jti` があればそれを使い、無ければ `sha256(idToken)` の hex。
     LINE の一次資料のペイロード一覧に `jti` は無い [実測: 2026-09-24 時点]ので、
     実運用では常に後者になる。将来 `jti` が増えたら自動的にそちらを使う実装にしてある。
   - 保存期間（TTL）はトークンの `exp` まで。`exp` を過ぎた行は
     `/api/cron/idempotency-cleanup`（task_020）が削除する。トークン自体が期限切れなら
     再提示しても `exp` 検査で落ちるので、行を残す意味がない。
   - **生の ID トークンは保存しない。** 保存するのはハッシュだけである。
3. **時刻のずれの許容は 60 秒に固定する。**
   - `exp`: `now > exp + 60` を拒否（期限切れ）。
   - `iat`: `iat > now + 60` を拒否（未来発行）。
4. `/api/auth/line` に **IP 単位のレート制限**を掛ける。保存先は Workers の
   Rate Limiting バインディング、無ければ Durable Object。**アイソレート内メモリは使わない**
   （A27。`docs/vendor-docs/cloudflare/rate-limiting.md`）。バックエンドが 1 つも
   束縛されていない場合は通すのではなく 503 で落とす（fail-closed）。
5. `aud` はサーバー側でも `LINE_ENV_PROFILE.loginChannelId` と突き合わせる。
   LINE 側が `client_id` で検証してくれるが、環境取り違え（R-LINE-04）は
   「LINE 側の検証は通るが自分が期待した環境ではない」形でも起きうるため二重にする。
6. **`/api/auth/line` はクロスサイトからの送信を受け付けない**（2026-09-24 追記。
   敵対レビュー F-1 を受けた決定。`src/lib/auth/request-guard.ts`）。
   `Origin` が自サイトと一致しない・`Origin` も `Sec-Fetch-Site: same-origin` も無い場合は 403、
   `Content-Type` が `application/json` でない場合は 415、本文に `idToken` 以外のキーがある場合は 400。
   理由は下の「消えないリスク」に足したとおりで、**単回使用もレート制限も
   「攻撃者自身の未使用トークンを被害者のブラウザから送らせる」形を止められない**ためである。

## 帰結

- ID トークンを盗んでも、正規の利用者が先に使っていれば再利用できない。
  盗んだ側が先に使った場合は正規の利用者が 401 になり、再ログインで気づける。
- `used_id_token` の行数はログイン回数に比例して増える。TTL は最長 1 時間なので
  定常状態では「直近 1 時間のログイン数」で頭打ちになる。
- **消えないリスク**: 単回使用は「同じトークンの 2 回目」しか止めない。
  攻撃者が正規利用者より先に 1 回目を使えば、その 1 回でセッションが取られる。
  ここは ID トークンの露出そのもの（ログ出力禁止・通信路）と、
  `session_epoch` による事後の一括失効（R-SEC-10）で受ける。
- **単回使用が守らないもの（2026-09-24 追記）**: 上と裏返しの形として、
  **攻撃者が「自分の」未使用トークンを被害者のブラウザから送らせる**経路がある。
  トークンは未使用なので単回使用の検査を通り、IP 単位のレート制限も初回の 1 通は拒否しない。
  成功すると被害者のブラウザに**攻撃者の**セッションが入り、以後その人が行う操作
  （同意・イベント作成・請求の確定）が攻撃者のアカウントに記録される
  （ログイン CSRF / セッション固定）。これは ID トークンの性質では防げないので、
  決定 6 のリクエスト検査（同一オリジン / JSON / 未知フィールド拒否）で受ける。
- **消えないリスク**: Rate Limiting バインディングは
  「拠点ごとに別カウンタ・結果整合」と一次資料が明言しているため、全球で厳密な閾値にはならない。
  厳密さが要る場合の逃げ道として Durable Object 版の実装を同じインターフェースの裏に置いた。

## 却下した案

| 案 | 却下理由 |
|---|---|
| `liff.login({ nonce })` でサーバー発行の nonce を渡す | LIFF ブラウザ内での `liff.login()` の動作が LINE の一次資料で保証されていない。主経路で成立しない対策を主対策にできない |
| ID トークンを検証せずクライアントの `getDecodedIDToken()` を信じる | LINE が明示的に禁止（N2）。論外 |
| 単回使用をアイソレート内メモリで持つ | Workers はアイソレート間でメモリを共有しない。本番で機能しない（A27） |
| 単回使用を止めて `exp` 検査だけにする | R-SEC-08 そのもの。1 時間の再利用窓が開いたままになる |

## 再検討の条件

- LINE が LIFF ブラウザ内の `liff.login()` の動作を保証する記述を出した場合。
- `verify` のレスポンスに `jti` が追加された場合（キーの取り方が変わるだけで決定は変わらない）。
- A27 の実測（task_024）で Rate Limiting バインディングも Durable Objects も使えないと判明した場合。
  その場合のフォールバックは Postgres のカウンタ表（§7-2 に記載済み）であり、この ADR の
  1〜3 は変わらない。
